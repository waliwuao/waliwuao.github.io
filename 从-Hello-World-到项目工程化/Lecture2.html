引言

在前面两篇文章中，我们完成了计算器项目的文件结构设计和环境管理配置。但还有一件事悬而未决——你怎么保存这个项目的迭代历史？

目前你的工作流可能是这样的：项目改了一点 → 另存为 calculator_v2.py → 又改了 → calculator_final.py → 又改了 → calculator_final_real.py。一周后，面对满屏幕的 final、v3、backup，你已经不知道哪个版本才是「真的能跑的那个」。

版本控制系统（Version Control System，VCS） 就是为解决这个问题而生的。它像一台时光机，让你随时回到项目的任何一个历史时刻、对比任意两个版本之间的差异、让多人并行工作而不会互相踩踏。

本文将带你从零掌握 Git——当今最主流的版本控制系统，以及 GitHub Flow——最广泛使用的协作流程。

阅读前提：你会用终端运行命令，了解目录和文件的基本操作。无需任何 Git 经验。

第一部分：为什么需要版本控制？

没有 Git 的世界

想象你正在开发计算器项目。今天你决定重构 add.py，把纯 Python 实现换成 NumPy 向量化版本。你改了几十行代码，测试通过，信心满满。

过了两天，你发现重构后的代码在矩阵运算中引发了性能问题，但你已经改动了另外五个文件。你想退回重构之前的代码——做不到。你没有保存那时的快照。

更糟的是，你和同学同时修改了 main.py。你改完发给他，他覆盖了你的改动，你覆盖了他的改动——来回几次之后，main.py 变成了谁也看不懂的缝合怪。

没有版本控制的项目，这三个问题无法避免：

问题后果
无法回溯改了代码跑不起来，无法回到「上次能跑」的状态
无法协作多人同时修改，互相覆盖，没有合并机制
无法追溯三个月后看某段代码，不知道是谁写的、为什么那样写

Git 能做什么

Git 给你三样核心能力：

  1. 快照（Commit）：每次改动都可以保存为一个快照，像游戏存档一样。
  2. 分支（Branch）：你可以开一条「实验性分支」，在上面任意折腾，不污染主代码。搞砸了就删掉分支，一切如初。
  3. 合并（Merge）：你的分支和同学的分支可以自动合并到一起，冲突时有精确提示。

第二部分：Git 核心概念

Git 不是云端，是本地优先

一个常见误解：Git = GitHub。实际上：

  • Git 是跑在你本地的版本控制工具，不需要网络也能用
  • GitHub 是托管 Git 仓库的云端平台，用于协作和备份

你的项目加上 Git 之后，变成了一个 仓库（Repository，简称 repo）。仓库根目录下多了一个隐藏文件夹 .git/，它保存了项目的全部历史。

Git 的三个区域

理解 Git 的工作方式，关键是要区分三个「区域」：

工作目录（Working Directory）         你正在编辑的文件
         │  git add
         ▼
暂存区（Staging Area）               准备提交的快照
         │  git commit
         ▼
本地仓库（Repository）               永久保存的历史记录
         │  git push
         ▼
远程仓库（Remote Repository）         GitHub 上的副本
  • 工作目录：就是你的项目文件夹。你在这里写代码、删代码、改代码。
  • 暂存区：你告诉 Git「我下次提交要包含这些改动」。你可以只暂存一部分文件，而不是一锅端。
  • 仓库：Git 把暂存区的内容打包成一个不可变的历史节点，这就是一个 commit。

关键理解：git add 不是「保存」，git commit 才是。add 是你挑选哪些改动进入下一次快照，commit 才是按下快门。

第六部分：GitHub Flow 协作流程

GitHub Flow 是目前最主流的团队协作流程，核心就 6 步：

1. 从 main 创建功能分支
2. 在分支上开发和提交
3. 推送到 GitHub
4. 创建 Pull Request（PR）
5. 代码审查（Code Review）
6. 合并到 main 并部署

完整示例

场景：你要给计算器添加「求平方根」功能。

然后在 GitHub 上：

  1. 打开仓库页面，会看到提示「Compare & pull request」，点击它
  2. 填写 PR 标题和描述，说明你做了什么
  3. 点击「Create pull request」
  4. 同学（Reviewer）查看你的代码变更，在具体行上留言
  5. 你根据反馈修改，推送新 commit，PR 自动更新
  6. Review 通过后，点击「Merge pull request」
  7. 删除远程分支（GitHub 提供一键按钮）

为什么用 PR 而不是直接合？

直接 push mainGitHub Flow (PR)
没有审查环节，bug 直入主干至少一人审查，拦截低级错误
没有讨论记录，决策不可追溯PR 评论区记录所有讨论和决策
冲突发现晚，一合就炸分支隔离，冲突在 PR 阶段暴露
只有结果，没有过程PR 的每个 commit、每条评论都是知识沉淀

总结：Git 的基本心智模型

你写的代码  →  git add（暂存）  →  git commit（存档）  →  git push（发布）
                          ↓
                      git stash（暂存不提交）

别人的代码  ←  git pull（拉取+合并）  ←  origin（GitHub）

新手最常犯的错误

错误正确做法
直接在 main 上开发创建功能分支，合完删掉
commit message 写「update」写清楚改了什么：feat: / fix: / refactor:
不 pull 就 pushgit push 前先 git pull --rebase
.venv/ __pycache__/ 被提交配置 .gitignore，一劳永逸
merge 后不删分支git branch -d <分支名> 保持分支列表干净

三条黄金规则

  1. 早提交、频提交：每完成一个可运行的小改动就 commit，不要攒几十个改动一次性提交。
  2. 一个分支做一件事：feat-matrix 只改矩阵相关代码，不要顺手「顺便修个 typo」。保持分支粒度小、合得快。
  3. pull 再 push：每次 push 前先 pull 最新代码，提前发现冲突，在本地解决比在 PR 里解决容易得多。
