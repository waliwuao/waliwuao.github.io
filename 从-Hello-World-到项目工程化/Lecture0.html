引言

当你刚开始学习编程时，一个「能跑就行」的 main.py 可能就是全部。但随着功能的增加、协作者的加入，你会发现——文件组织不是一种负担，而是一种生产力。

本文以一个「计算器项目」的演变为线索，带你一步步理解：为什么我们需要合理的文件结构，以及如何渐进地设计它。

阅读前提：你只需要了解 Python 的基本语法（函数、import、列表/字典），对命令行（终端）有基本概念即可。

第一阶段：最初的 main.py

最初你是一个人开发。你的第一个作品是一个加法计算器：用户输入两个数，程序输出它们的和。

你创建一个文件，命名很直接——main.py：

此时的文件结构：

calculator/
└── main.py

一切都很简单。你运行 python main.py，输入两个数，得到结果——这就是编程最初的快乐。

第二阶段：功能膨胀

你接着往 main.py 里面添加了减法、除法、乘法的逻辑，让这个计算器支持四则运算：

接着你为计算器编写了更复杂的交互逻辑：循环选择运算 → 输入第一个数 → 输入第二个数 → 显示结果 → 返回主菜单。代码量很快来到了 80 多行。

这时候你发现 main.py 已经不对劲了：

  • 每次想看某一项运算的逻辑（比如除法的除零处理），你要在文件里翻半天
  • 想改一个地方，总担心牵一发而动全身
  • 代码越长，定位 Bug 越慢

这是你在编程路上遇到的第一个「结构性痛苦」——单一文件承载了太多职责。

第三阶段：第一次拆分

你决定按功能模块拆分。把每种运算的逻辑抽出来，各自放进一个独立文件：

  • main.py —— 只负责交互逻辑（用户输入输出、菜单选择）
  • add.py —— 加法
  • sub.py —— 减法
  • mul.py —— 乘法
  • div.py —— 除法

此时的文件结构：

calculator/
├── main.py
├── add.py
├── sub.py
├── mul.py
└── div.py

效果立竿见影：

  • 每个文件的职责单一，定位功能不再需要查找半天
  • 修改加法逻辑，你只需要打开 add.py，不怕影响除法
  • main.py 从 80 行缩减到 30 行，可读性大幅提升

核心原则：一个文件只做一件事（Single Responsibility）。这不是教条，而是你在 80 行的 main.py 里翻代码翻出来的体感。

第四阶段：数据与资源的分离

接着你决定实现预存常用参数的功能——用户不用每次输入 π 和 e，直接引用就好了。

你用两份文件来储存常量：

  • pi.py —— 储存 π
  • e.py —— 储存自然常数 e

此时文件结构：

calculator/
├── main.py
├── add.py
├── sub.py
├── mul.py
├── div.py
├── pi.py
└── e.py

随着文件增多，你发现项目根目录同一层级的文件有 7 个，而且并不是同一类东西——有的是「运算逻辑」，有的是「静态数据」。这让你开始感到「眼花缭乱」，每次打开项目都要扫一眼才能找到目标。

你做了一个关键决定：引入文件夹进行分类。

  • 创建 src/ 目录，放入所有运算逻辑文件
  • 创建 data/ 目录，放入常数文件
  • 项目根目录只留 main.py（启动入口）
calculator/
├── main.py
├── src/
│   ├── __init__.py
│   ├── add.py
│   ├── sub.py
│   ├── mul.py
│   └── div.py
└── data/
    ├── __init__.py
    ├── pi.py
    └── e.py

关于 __init__.py：在 Python 中，包含 __init__.py 的目录会被识别为一个 包（package），允许你用 from src.add import add 的方式导入。即使文件为空，也要加上它——这是 Python 导入机制的基石。

阶段性目标：让一个刚打开项目的人，3 秒内知道「核心入口在哪、功能在哪、资源在哪」。

第六阶段：子包与模块分层

然而好景不长。矩阵运算的加入让 src/ 目录又变得臃肿——现在是 7 个文件挤在一起。基础运算和线性代数混在一起，新同学打开 src/ 依然要「猜」哪个文件是做什么的。

你做了一个二级分类：在 src/ 下创建 base/ 和 linear/ 两个子包：

calculator/
├── main.py
├── README.md
├── src/
│   ├── __init__.py
│   ├── base/               # 基础运算
│   │   ├── __init__.py
│   │   ├── add.py
│   │   ├── sub.py
│   │   ├── mul.py
│   │   └── div.py
│   └── linear/             # 线性代数运算
│       ├── __init__.py
│       ├── mat_mul.py
│       ├── mat_scalar.py
│       └── mat_inverse.py
└── data/
    ├── __init__.py
    ├── pi.py
    └── e.py

src/ 目录瞬间清爽了：一打开就知道 base/ 是基础运算，linear/ 是高级运算。导入路径也随之改变：

分层原则：如果一个目录下的文件超过了 5-7 个，且存在自然的「类别」边界（比如「基础运算」vs「线性代数」），就应该考虑创建子包。

第七阶段：依赖管理——pyproject.toml

一个更有经验的同学加入了项目。他发现你们的运算实现都是纯 Python，性能不是最优。他建议引入 NumPy，利用其底层 C 实现来优化矩阵运算。

这听起来很美好——但你和他分别在自己的电脑上执行了 pip install numpy 之后，运行同样的代码却产生了不同的结果！

原来你装的是 numpy==1.26.0，他装的是 numpy==2.1.0。虽然语法上无差别，但某些 API 的返回类型和行为在不同版本间有细微变化，导致你的代码在他的环境下报错。

这就是「在我机器上能跑」问题的根源——环境不一致。

为了解决这个问题，你们创建了 pyproject.toml 文件，明确声明项目依赖的库及其版本：

文件结构更新为：

├── README.md
├── pyproject.toml          # 项目元信息与依赖声明
├── src/
│   ├── __init__.py
│   ├── base/
│   │   ├── __init__.py
│   │   ├── add.py
│   │   ├── sub.py
│   │   ├── mul.py
│   │   └── div.py
│   └── linear/
│       ├── __init__.py
│       ├── mat_mul.py
│       ├── mat_scalar.py

第八阶段：引入测试——pytest

你通过学习 NumPy 的文档，成功用向量化运算优化了矩阵相乘，原本需要 2 秒的 1000×1000 矩阵乘法现在只需要 0.03 秒。你兴奋地测试了 1×1 矩阵，没问题。于是提交了代码。

第二天，同学说他运行时崩溃了——只要输入的矩阵元素超过 100000，程序就抛出异常。原来 NumPy 的默认数据类型 int64 在大数值乘法中会溢出，而你只测了「1+1=2」那种 trivial case。

你意识到一个痛点：手工测试只会覆盖你「觉得」应该测的场景，而真正的 Bug 往往出现在你没想到的边界。

于是你引入 pytest 来自动化测试。创建 tests/ 目录：

总结：文件结构演进的核心原则

回顾整个项目从 1 个文件到如今 20+ 个文件的过程，你经历的根本不是「文件变多了」，而是复杂度被拆解成可管理的单元。每一次重构都解决了一类特定的痛点：

阶段痛点解决方案
单文件膨胀代码过长、职责不清按功能拆分文件
文件平铺类型混乱、层次不清引入 src/ 和 data/ 分类
协作者加入不知道如何上手编写 README.md
子模块增多src/ 下过于拥挤子包分层（base/、linear/）
环境不一致「在我机器上能跑」pyproject.toml 锁定依赖版本
手工测试不可靠Bug 漏过边界情况pytest 自动化测试

三条经验法则

  1. 关注当下，不过度设计：不要在只有 2 个文件时建 5 层目录。当「肉眼扫不过来」时再拆分。
  2. 一个模块一个职责：如果你描述一个文件的功能需要用「和」字（比如「负责加法和乘法」），就该拆开了。
  3. 让新成员 3 分钟跑起项目：README + pyproject.toml 的组合，让任何有 Python 环境的人做到 pip install -e . && python main.py 即运行。

不同项目类型的常见约定

根据项目类型，你可能还会遇到这些结构惯例：

项目类型常见额外目录
ROS 2 包launch/、config/、msg/、srv/
Web 应用templates/、static/、migrations/
数据科学/MLnotebooks/、models/、data/、configs/
CLI 工具bin/ 或 scripts/

学会文件结构设计，本质上是在学习如何让代码可以被别人（包括 3 个月后的自己）理解和维护。这比写出一个能跑的算法，更难，也更重要。
